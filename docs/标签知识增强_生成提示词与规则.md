# 标签知识增强：CSV / JSON 生成提示词与补充规则

> 用途：让其他语言模型在当前标签名基础上补充标签定义、常见表达、正例、反例和易混边界。
>
> **项目同时提供 CSV 和 JSON 两种模板，字段完全一致。每批任务任选一种格式：输入 CSV 就返回 CSV，输入 JSON 就返回 JSON。**所属类别、细分类别不参与生成。

---

## 一、需要提供给生成模型的文件

1. 本规则文档：`docs/标签知识增强_生成提示词与规则.md`；
2. 根据使用习惯，二选一：
   - `data/标签知识增强_生成模板_638.csv`；
   - `data/标签知识增强_生成模板_638.json`；
3. 本文第四节的“完整提示词”。

两份模板都包含 **638 个标签、23 个固定字段**，已预填“标签ID、标签名、现有常见表达”，其余 20 个字段留空。

建议：

- 每批处理 **20～30 个标签**；
- 第一批处理前 20 个标签；CSV 对应 Excel 第 2～21 行，JSON 对应数组第 1～20 项；
- 每批另存为新文件，例如 `标签知识增强_已填写_批次01.csv` 或 `.json`，不要覆盖原空白模板；
- 一批只要求模型填写一种格式，另一种格式后续通过脚本转换，避免让模型重复生成造成内容不一致；
- 先验收第一批质量，再继续后续批次，不要第一次就生成全部 638 项。

## 二、字段结构与填写要求

| 字段（也是 CSV 列名 / JSON 键名） | 是否预填 | 填写要求 |
| --- | --- | --- |
| 标签ID | 是，禁止修改 | 当前项目的稳定映射 ID，必须原样保留 |
| 标签名 | 是，禁止修改 | 不得改名、拆分或合并 |
| 现有常见表达 | 是，禁止修改 | 只作参考，不直接在此字段增删 |
| 标签定义 | 否 | 用 50～120 个汉字说明什么帖子表达算该标签 |
| 补充后常见表达（完整列表） | 否 | 填写合理原表达＋新增表达的完整合集，用顿号“、”分隔 |
| 正例_明确含标签名 | 否 | 1 条包含标签名且语义明确成立的社媒短句 |
| 正例_语义1～3 | 否 | 3 条尽量不含标签名、但语义明确成立的社媒短句 |
| 反例1～3 | 否 | 3 条容易误判但不应打标的近失例 |
| 反例1原因～反例3原因 | 否 | 分别解释对应反例为什么不能打标 |
| 易混标签1～3 | 否 | 填写真实存在、容易与当前标签混淆的标签名 |
| 易混边界1～3 | 否 | 分别说明当前标签与对应易混标签的区别、能否同时成立 |
| 是否需人工复核 | 否 | 只能填“是”或“否” |
| 复核原因 | 否 | 填“是”时必须写明原因；填“否”时留空 |

### 通用字段要求

1. 保持原来的 **23 个字段及字段顺序**，不得新增所属类别、细分类别或其他层级字段。
2. 不得增删、复制或调换标签；每项只填写当前标签的内容。
3. “补充后常见表达（完整列表）”不是“只填新增词”，而是填写去重后的完整列表。
4. 多项常见表达统一用顿号“、”分隔；两种格式都使用字符串保存该完整列表，便于一比一转换。
5. 文件保持 **UTF-8 编码**，不要在数据前后增加说明、总结或 Markdown。

### CSV 格式要求

1. 保持 23 列及列顺序，不得增删标签行。
2. 单元格内部尽量不使用换行。
3. 内容含英文逗号、双引号等字符时必须遵守标准 CSV 转义规则，不能破坏后续列的对齐。
4. 保存为 `.csv`，不要在表格前后增加说明行或总结行。

### JSON 格式要求

1. 顶层必须是数组，包含 638 个对象；每个对象使用与 CSV 完全相同的 23 个键。
2. 不得把顶层数组改成以“数据”“结果”等命名的包装对象。
3. 所有字段值均使用字符串；未处理字段保留空字符串，不使用 `null`、布尔值或数组替代。
4. 必须输出合法 JSON：字符串使用双引号，不使用尾逗号，不添加注释。
5. 保存为 `.json`，不要改成 JSONL（每行一个对象）。

## 三、必须遵守的补充规则

### 1. 标签映射规则

1. `标签ID` 和 `标签名` 必须原样返回，不能遗漏、增加、改名、拆分或合并标签。
2. 不使用、不推测所属类别和细分类别，不输出这两个字段。
3. 不创造新的标签体系，不补充医疗诊断、治疗承诺或未经证实的功效事实。
4. 同名不同 ID 的标签不得依赖类别进行区分；按相同标签文本处理，并将无法消除的歧义标记为 “是否需人工复核”=“是”。

### 2. 标签定义规则

定义必须面向“社媒帖子是否提及该标签”，包括：

- 哪类表达可以算；
- 是否允许同义改写、口语表达；
- 必要的语义边界。

定义不应：

- 写成成分或功效的百科介绍；
- 宣称未经证实的医学、功效或安全结论；
- 仅把标签名换一种方式重复一遍；
- 引入所属类别、细分类别；
- 把“提到成分”直接推导成“提到该成分功效”。

### 3. 常见表达规则

优先补充：

- 同义词、近义表达；
- 常见社媒口语；
- 常见缩写、谐音、黑话，但必须确实存在且含义稳定；
- 能明确指向该标签的短语。

不得为了凑数加入：

- “好用、喜欢、推荐、分享、效果”等几乎所有标签都能使用的泛词；
- 只有结合多个线索才可能成立的弱提示词；
- 与标签仅有宽泛主题关联的词；
- 编造的网络用语、缩写和谐音；
- 品牌名、产品名，除非它本身就是标签不可分割的一部分。

`现有常见表达` 中的合理表达默认保留并去重。发现明显错误时不要静默删除，将其问题写入 “复核原因”，并设 “是否需人工复核”=“是”。

### 4. 正例规则

每条正例必须是符合项目打标语境的**虚构社媒帖子短句**，不要使用真实用户、真实帖子或编造引用来源。

- `正例_明确含标签名`：包含标签名本身，并且语义明确成立；
- `正例_语义1～3`：尽量不出现标签名，用同义表达或明确情境体现标签；
- 正例之间应有表达差异，不要只替换主语或产品名；
- 不依赖读者具备某款产品的外部知识；
- 不把所有正例都写成广告文案，应覆盖用户分享、体验描述等自然表达。

### 5. 反例规则

反例必须是“看起来容易混淆，但按定义不应打标”的近失例，并给出具体原因。优先考虑：

- 明确否定；
- 仅提到相关成分，但没有表达对应功效；
- 话题相关但标签语义不成立；
- 与易混标签含义更接近；
- 评价对象不对应。

**与强正则的一致性要求**：如果反例中包含标签名本身，必须在标签附近写出清楚否定，确保不会被“标签名精确出现且附近无否定”的规则直接打标。不要为了构造反例而写一个“标签名干净出现但又不算”的矛盾示例；遇到这种口径争议应标记人工复核。

### 6. 易混边界规则

每条边界必须写清：

- 易混标签是什么；
- 什么表达应归当前标签；
- 什么表达更接近另一个标签；
- 两者是否可以在同一帖子中同时成立。

优先从本批输入或另行提供的完整标签清单中，选择要填入“易混标签”列的标签名。不确定另一个标签是否存在时，不要编造标签名，可以减少边界数量或标记复核。

### 7. 不确定性与审核规则

遇到以下情况必须设 “是否需人工复核”=“是”：

- 标签名本身过短、过宽或存在多种常见含义；
- 无法确定标签在美妆社媒语境中的具体含义；
- 常见表达容易引入大量误标；
- 正例、反例与当前强正则规则存在冲突；
- 易混边界没有把握。

**宁可少生成，也不要编造。**不得虚构外部资料、法规、论文、链接或引用。

## 四、可直接交给其他模型的完整提示词（CSV / JSON 通用）

将下面提示词整段复制给生成模型，并同时提供本规则文档，以及 CSV 或 JSON 模板中的一种：

```text
你是“美妆社媒标签知识增强助手”。请阅读我提供的《标签知识增强_生成提示词与规则》，并直接填写我提供的标签知识增强模板。

本次任务支持两种文件格式：
- 如果我提供的是 CSV，你必须返回填写后的 CSV；
- 如果我提供的是 JSON，你必须返回填写后的 JSON 数组；
- 输入什么格式就返回什么格式，不要改成另一种格式，不要输出 JSONL、Markdown 表格或文字说明代替文件内容。

一、文件结构要求
1. 保持原模板的23个字段、字段名和字段顺序不变，保持638个标签的数量及顺序不变。
2. 标签ID、标签名、现有常见表达三个字段必须原样保留，不得修改。
3. 不得增删标签，不得新增所属类别、细分类别或其他层级字段。
4. 只在当前标签对应的空白字段填写内容，不得串用其他标签的内容。
5. 文件使用 UTF-8 编码。CSV 要遵守标准 CSV 转义；JSON 顶层必须是数组，每项是含相同23个键的对象，所有字段值使用字符串，不使用 null、尾逗号或注释。

二、需要填写的内容
1. 标签定义：50～120个汉字，说明“什么社媒帖子表达算该标签”，不写百科，不虚构医学、功效或安全事实，不把成分出现直接等同于功效出现。
2. 补充后常见表达（完整列表）：填写合理的现有表达与新增表达的完整合集，用顿号“、”分隔。只收明确指向该标签的同义词、口语、缩写、谐音或短语；不得编造网络用语，不得加入“好用、喜欢、推荐、分享”等泛词。过窄标签可以少给，不为了凑数添加弱相关词。
3. 正例：填写1条“正例_明确含标签名”和3条“正例_语义1～3”。每条15～50个汉字，均为虚构、自然的社媒短句。明确正例包含标签名且语义成立；语义正例尽量不含标签名，但语义明确成立。4条正例要有表达差异。
4. 反例：填写3条近失例及各自原因。优先使用明确否定、成分不等于功效、话题相关但语义不成立、易混标签或评价对象不对应。若反例含标签名，标签附近必须有清楚否定，不得与“标签名精确出现且附近无否定就直接打标”的强正则规则冲突。
5. 易混边界：填写2～3组易混标签和对应边界，说明什么表达归当前标签、什么表达更接近另一个标签、两者能否同时成立。不确定时可以少填或留空，不编造标签。
6. 复核：遇到过宽、歧义、生成信心不足、容易引入大量误标、原表达明显有问题或与强正则规则冲突时，“是否需人工复核”填“是”，并写清复核原因；其他情况填“否”，复核原因留空。宁可少生成或标记复核，也不要编造。

三、通用限制
1. 不使用、不推测所属类别和细分类别。
2. 不虚构外部资料、链接、法规、论文、品牌事实或真实用户案例。
3. 不生成医疗诊断、治疗承诺或未经证实的功效结论。
4. 同名不同ID不得依赖类别进行区分；无法消除的歧义应标记人工复核。
5. 所有例子都应是虚构内容，不得冒充真实帖子或引用。

四、本批处理范围与交付
1. 本批只处理我指定的前20个标签，不要处理其余项，不要重排或删除未处理项。
2. 返回填写后的完整文件，文件名使用“标签知识增强_已填写_批次XX.csv”或“标签知识增强_已填写_批次XX.json”，扩展名与输入一致。
3. 如果平台支持文件输出，直接提供可下载文件；如果确实不能生成文件，则输出对应格式的完整文本，但仍须保持原23个字段及格式合法。
4. 不要同时重复生成 CSV 和 JSON 两份内容；后续由项目脚本进行格式转换，避免两份内容不一致。
5. 完成后简要报告：本批处理了多少个标签、多少个标记人工复核；报告不要写入数据文件内部。

请先处理模板中的前20个标签。
```

后续批次只需把最后的处理范围改成对应行号或数组序号，并将“批次XX”替换为实际批次号。

## 六、生成后的验收清单

每批结果回来以后，至少检查：

- [ ] 文件格式与输入一致：CSV 返回 CSV，JSON 返回 JSON 数组；
- [ ] 仍为 23 个字段，字段名和顺序未变；
- [ ] 标签ID、标签名、现有常见表达及标签顺序与原模板一致；
- [ ] 本批 20 个标签均已填写，其他标签没有误改；
- [ ] 没有所属类别、细分类别或额外层级字段；
- [ ] 补充后常见表达是完整列表，并使用顿号分隔；
- [ ] 定义不是标签名复读，也没有无依据的功效事实；
- [ ] 常见表达没有明显泛词、编造黑话或大量弱相关词；
- [ ] 1 条明确正例、3 条语义正例、3 条反例及原因均已填写；
- [ ] 含标签名的反例附近有明确否定，不与强正则直接打标冲突；
- [ ] 易混标签真实存在，边界不是强行编造；
- [ ] “是否需人工复核”只填“是/否”，填“是”的复核原因完整；
- [ ] CSV 没有串列、漏列、单元格换行破坏或额外总结行；
- [ ] JSON 顶层是数组，字段值均为字符串，没有 `null`、尾逗号、注释或 JSONL；
- [ ] 人工抽检通过后才进入 RAG 实验。

## 七、接入 RAG 时的重要规则

**反例和易混边界不建议直接拼进第一版 embedding 文本。**它们与目标标签在字面上很相似，全部向量化后可能反而提高误候选率。

建议先做两版对照：

```text
基线版：标签名＋现有常见表达
增强版：标签名＋标签定义＋审核后的常见表达＋正例
```

反例和易混边界先用于：

- 人工审核；
- Jev 问法和边界规则优化；
- 误标、漏标分析；
- 后续单独设计对照实验。

不要拿最终测试集的标准答案反向生成知识再评测同一批数据，以免答案泄漏。建议使用独立训练资料、通用语言知识和人工审核生成标签卡片。
