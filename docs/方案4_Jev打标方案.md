## 1. 核心任务

对 `data\抽样清单.csv` 指定的帖子，调用 Jev API 判断每个标签是否被提及，生成 17 列预测细分表和 12 列预测汇总表。

**所有标签命中结论均来自 Jev API 返回的概率。** 本地代码负责准备请求、发送 API、保存响应、按阈值转换概率、辅助生成证据和情绪。

## 3. Jev 问题类型选择：Noul vs Choice vs Score

| 原语 | 模型回答 | 适合任务 | 是否适合本次 638 标签主任务 |
| --- | --- | --- | --- |
| **Noul（判断）** | 是/否概率（0~1） | 是非判断、条件清单、多标签命中 | **适合** |
| **Choice（选择）** | 从选项中选一个 + 各选项概率 | 单选分类、路由 | **不适合**：一条帖子可命中多标签，不能只选一个 |
| **Score（打分）** | 在有序等级中选一个 | 严重程度、满意度 | **不适合**：词库没有为每个标签定义统一强度等级 |

**选 Noul 的四个理由**：
1. 多标签任务，一条帖子可命中多个标签；
2. 需要独立概率做阈值和灰区；
3. 不需为每个标签构造"命中/未命中"两选项；
4. 词库没有评分标尺。

Choice/Score 留作辅助字段：后续补产"表达类型""情绪"等互斥属性时用 Choice；增加"严重程度"等有序指标时用 Score。

### 4.1 方案 A1：全量纯语义（638 问）

**思路**：每个标签只问"是否提到「X」（类别）？"不加任何词库命中/排除提示。

**用途**：测量 Jev 的裸语义能力上限——不借助词库提示时能得多少分。

**token/帖**：约 27k（state 约 4k + 638 × 35 tok/问）。

**10,000 条成本**：约 ¥138。

### 4.2 方案 A2：全量+词库提示（638 问）⭐ 当前推荐

**思路**：每个标签问"是否提到「X」（类别）？常见说法如 A、B、C，同义改写也算；若语境是否定/排除含义则不算。"

**用途**：Jev 效果基准——给出"Jev 在词库辅助下能做到多少分"的上限。

**token/帖**：约 86k（state 约 4k + 638 × 130 tok/问）。

**10,000 条成本**：约 ¥259。

### 4.3 方案 B：词库粗筛后 Jev（约 30 问）

**思路**：先用词库规则（命中关键词 + 且词 + 排除词）在本地做正则匹配，只对命中的标签调用 Jev 验证。

**token/帖**：约 5k（只有命中的候选标签进入 API）。

**10,000 条成本**：约 ¥16。

**优点**：成本极低，适合预算紧张或大批量。
**缺点**：
- 纯语义标签（108 行命中词与标签名零交集）天然漏掉；
- 谐音黑话（m感/k氧/早C晚A）正则匹配不到；
- 召回上限受限于正则覆盖率。

**📊 2026-11-16 实测修正（100 条，tau=0.6，对齐 LLM 初稿金标准）**

| 指标 | 实测值 |
| --- | --- |
| 准确率 P | **49.5%**（677 / 1,368） |
| 召回率 R | **37.5%**（677 / 1,805） |
| F1 | 0.427 |
| 字面匹配召回天花板 | **71.2%** |

三个必须先认清的事实：

1. **B 方案在结构上不可能达到 95%。** 金标准 1,805 个标签里只有 1,285 个能在原文找到
   词库关键词的字面形式，剩下 520 个是同义改写/隐含表达，字面粗筛永远捞不到。
2. **召回问题 95% 出在粗筛，不在模型。** 1,128 个漏标里有 1,076 个是"压根没送进模型"，
   只有 52 个是送问了却没判对。
3. **准确率 49.5% 才是 Jev 自身的问题。** 送问的 1,368 个标签里有 691 个假阳性，
   要靠问题措辞优化或收窄金标准口径来解决。

**已修复的两个实现缺陷**（详见 `core/README.md` §3）：

- 排除词旧版按全文匹配：362 个标签共用"不/没/没有/没用…"这套通用否定词，
  中文帖子几乎都含"不"字，候选被大面积误杀（每帖候选 21.1 → 修复后 34.4）。
- 粗筛用 `full_text` 全文、送模型只送前 2000 字：在 2000 字之外命中的标签会被提问，
  但模型从来看不到那段文字，必然判 0。

**定位建议**：B 方案可保留为"低成本预筛层"，但不能作为独立交付方案去承诺 95% 准确率。

### 4.4 方案 H：两级级联（类别门控 → 候选标签）

**思路**：
1. 第 1 次请求：问 41 个类别（Noul）；
2. 保留概率 ≥0.15 的类别 + Top-12 类别；
3. 第 2 次请求：只对候选类别下的叶子标签提问。

**token/帖**：约 16k（请求 1: ~2k + 请求 2: ~14k）。

**10,000 条成本**：约 ¥49（理想情况节省 81%）。

**优点**：纯 Jev 方案，不依赖正则/嵌入；大幅降本。
**缺点**：
- 门控可能漏召回（类别答错→整组子树消失）；
- 需要回退机制（门控不确定时回退全量）；
- 多次请求重复发送 state，抵消部分节省；
- 实现复杂（需要多轮请求编排）。

**实测数据**（理想父级全对时）：
- 两级（类别→标签）：平均 253 问/帖；
- 三级（类别→细分类别→标签）：平均 181 问/帖。

### 4.5 方案 RAG：语义检索 + Jev 验证（Top-50 标签）

**思路**：
1. 预计算 638 个标签描述的向量嵌入（一次性成本）；
2. 对每条帖子计算向量嵌入；
3. 余弦相似度取 Top-50；
4. 只对 Top-50 调用 Jev 验证。

**token/帖**：约 8k（50 问 × 130 tok + state 约 1.5k）。

**10,000 条成本**：约 ¥40（节省 85%）。

**优点**：最现代、最通用、不需要手写规则；大幅降本。
**缺点**：
- 需要额外嵌入模型 API（如 OpenAI text-embedding-3-small）；
- 可能漏掉"字面相似但语义不同"的标签；
- 依赖嵌入质量，召回不可控。

> ✅ **实现状态（2026-11-17 更新）**：RAG 已接入 OpenAI 兼容 embedding 接口，按帖子与标签向量的余弦相似度选 Top-K，并带本地缓存；H 已在客户端按 gate 真实概率动态筛选 leaf；Speculative 已按 pass1 边界概率筛选 pass2，并正确合并两轮结果。三者已通过离线测试，但真实 API 效果和成本仍待跑批验收。Hybrid 仍是旧原型，不在本次补齐范围内。

### 4.6 方案"混合"：正则 + Jev（约 200 问）

**思路**：
1. 用词库正则匹配所有能匹配的标签（约 400 个，零成本）；
2. 精确匹配且上下文符合 → 直接接受；
3. 精确匹配但有否定词/歧义 → 送 Jev 验证（约 100 个）；
4. 无匹配但在"纯语义标签"集合中 → 送 Jev 判断（108 个）；
5. Jev 总问题数约 200。

**token/帖**：约 16k。

**10,000 条成本**：约 ¥100（节省 61%）。

**优点**：最实用、不需要额外 API、召回可控。
**缺点**：需要维护两套逻辑（正则+Jev），工程复杂度高。

> 注：本节是早期 Hybrid 原型，其中“精确匹配直接接受”的思路不再作为新方案的默认口径。最新方案见 §4.8：只有“标签名精确出现且附近无否定”才由本地直接打标；否定命中和 RAG 候选统一交 Jev 复核。

### 4.7 方案"投机"：两级 Jev（638 → 150 问）

**思路**：
1. 第一遍用 A1 简短指令（638 问，约 27k token）；
2. 只对概率在 [0.2, 0.8] 的"边界标签"用 A2 详细指令（约 150 问）；
3. 边界标签用 A2 概率，其余用 A1 概率。

**token/帖**：约 32k（A1: 27k + A2 边界: ~5k）。

**10,000 条成本**：约 ¥200（节省 23%）。

**优点**：纯 Jev 方案，不需要其他模型。
**缺点**：节省幅度最小，实现复杂（需要两轮请求编排）。


### 4.8 HybridRAG：强正则直接打标＋RAG 语义召回＋Jev 复核（新，待真实 API 实验）

**方案定位**：用户确定的最新口径是：标签名在原文中明确出现，且前后没有否定时，由强正则直接打标，不再消耗一次 Jev；其余标签通过 RAG 检索候选，再交 Jev 判断。否定窗口中的精确命中不直接打标，但保留给 Jev 复核，防止双重否定或否定对象误判。

> **当前状态（2026-11-20）**：核心代码、直接标签写回、候选来源审计、向量用量统计和 v0.2.3 候选召回评测已补齐，23 项项目离线测试通过；真实 embedding/Jev API 验收和同样本对照实验仍待开展。旧 `Hybrid` 原型与本方案无关。

#### 4.8.1 强正则的准确含义

这里的“强正则”不是“看到任意近义词就直接打”，也不是“所有正则候选都送 Jev”，而是：

1. **只精确匹配标签名本身。**例如标签名是“保湿”，原文必须实际包含“保湿”；只出现“滋润”不能由强正则直接打“保湿”，只能等待 RAG＋Jev 判断。
2. **检查命中位置前后窗口。**默认使用词库 `near`，通常为 15 字，并检查该标签的排除词/否定词。至少一个精确命中位置未触发排除规则，就可直接打标。
3. **否定命中进入复核。**如“不是不保湿”，不直接打，但会进入 Jev，避免硬删除双重否定。
4. **多个命中位置分别判断。**前一个位置有否定、后一个位置没有否定时，仍可依据后一个干净命中直接打标。
5. **粗筛和模型使用同一截断文本。**默认前 2000 字，保证证据位置可复现。

示例：

| 原文 | 强正则结果 | 后续 |
| --- | --- | --- |
| 这款面霜保湿很好 | 直接打“保湿” | 不送 Jev |
| 这款很滋润 | 不能把“滋润”直接当“保湿” | 可由 RAG 找回后送 Jev |
| 这款不保湿 | 不直接打 | “保湿”进入 Jev 复核 |
| 不是不保湿 | 不直接打 | 双重否定交 Jev 复核 |
| 前文“不保湿”，远处后文明确“保湿很好” | 后一个干净命中可直接打 | 使用干净位置的证据 |

固定窗口仍不能完美理解否定对象，因此本方案保留否定复核，并单独统计强正则直接标签的 P/R，正式跑量前先检查直接打标是否足够精确。

#### 4.8.2 完整工作流程

设强正则直接标签集合为 `D`，否定精确命中的复核集合为 `R`，RAG Top-K 为 `S`：

```text
完整截断帖子 → 标签名精确匹配＋前后否定检查
                    ├─ 无否定：D，本地直接打标，0 Jev token
                    └─ 有否定：R，保留给 Jev 复核

完整截断帖子 → embedding 与638个标签定义计算相似度 → RAG Top-K = S

Jev送问集合 = (R ∪ S) - D
最终标签   = D ∪ { label | label ∈ Jev送问集合 且 Jev(label) ≥ tau }
```

- 已直接打标的标签即使进入 RAG Top-K，也不重复送 Jev；
- 否定复核与 RAG 重合时只问一次；
- RAG 使用完整帖子，不删除正则命中的句子；
- RAG 标签向量文本只使用“标签名＋词库常见表达”，暂不把不可靠的所属类别、细分类别拼入 embedding；
- embedding 相似度不是最终概率；强正则直接标签与 Jev 标签在结果中有明确来源区分；
- 实际 Jev 问数可能小于 Top-K，因为直接标签会被扣除；否定复核也可能额外增加少量问题。

#### 4.8.3 结果写回与可追溯

`schemes.py` 生成：

- `候选标签_HybridRAG.csv`：记录强正则 `direct/review`、是否直接打标、是否送问、精确命中证据、RAG 相似度与排名；
- `embedding_usage_HybridRAG.json`：记录向量请求、缓存命中和接口实际 usage；
- HybridRAG payload：`meta.hybrid_rag.direct_labels` 保存直接标签，`candidates` 保存 Jev 候选。

`jev_client.py` 正式运行时：

- 直接标签写成独立 `regex_direct` 阶段，本地概率为 1.0、token 为 0、模型为 `local-strong-regex`；
- Jev 候选写成 `leaf` 阶段；
- 下游合并两阶段，最终 CSV 的直接标签标记“强正则直接命中/本地强正则”，不伪装成 Jev 响应；
- 0 个 Jev 候选也会保留 skipped 记录，直接标签和空结果帖子都不会从评测范围消失。

| 方案 | 明确字面命中 | 语义候选 | 最终判断 |
| --- | --- | --- | --- |
| A2 | 638 个全部送 Jev | 不需要 | 全部 Jev |

#### 4.8.5 正式实验顺序

1. **先跑 50～100 帖 embedding，生成候选审计。**Top-K 扫描覆盖 20/50/100/200，不急着调用 Jev。
2. **先检查强正则直接打标质量。**报告直接标签数、其中标准答案正确数、直接准确率 P、直接召回率 R；若直接 P 明显偏低，先修精确匹配/否定窗口，不扩大跑量。
3. **检查候选覆盖。**分别看强正则、RAG 和两者并集的候选召回，以及平均每帖实际 Jev 问数。
4. **选择 1～2 个 Top-K 跑真实 Jev。**使用相同帖子、A2 问法和 tau 曲线，与 A2/B/纯 RAG 做同样本对照。
5. **最终按现行 v0.2.3 口径评测。**帖子 ID 对齐，只比较“标签”列，同帖同名标签去重，报告标准答案标签总数、micro P/R/F1、Jev token、embedding token 和综合成本。

候选召回与最终召回分开报告：

```text
候选召回率 = 进入“直接标签∪否定复核∪RAG Top-K”的标准答案标签数 ÷ 标准答案标签总数
强正则直接准确率 = 直接标签中属于标准答案的数量 ÷ 直接标签总数
强正则直接召回率 = 直接标签中属于标准答案的数量 ÷ 标准答案标签总数
```

只有强正则直接准确率符合预期、候选覆盖确实改善，并且最终 F1/综合成本优于更简单方案时，才扩大实验。

| 风险 | 低 | 中（召回/阈值需调试） |
| 适用场景 | 测试阶段、日处理<10万条 | 生产阶段、日处理>50万条 |

**结论**：10,000 条测试阶段，¥259 在预算内，A2 全量是最简单可靠的选择。先进方法留到生产阶段再考虑。

### 5.2 什么时候需要切换方案

| 场景 | 推荐方案 | 理由 |
| --- | --- | --- |

## 6. A2 方案的详细设计

### 6.1 调用 Jev 时的核心结构

#### state：帖子内容

```json
{
  "平台": "小红书",
  "内容": "【标题】……\n【正文】……\n【图片文字】……"
}
```

- 平台：从 v3 的 `site_name` 读取；
- 内容：从 v3 的 `full_text` 读取，最多 2,000 字；超长截断并在 meta 中标记。

**不发送**：金标准、入样原因、词库行号（这些只用于本地后处理）。

#### questions：638 个标签问题

每个标签一个 Noul，格式示例：

```json
{
  "q0001": {
    "type": "noul",
    "instructions": "这篇社媒内容是否提到了「干皮」（肤质类型）？常见说法如干皮、干燥、爆皮、起皮、脱皮、掉皮，同义改写也算。若语境是不干皮、不是干皮等否定/排除含义则不算。"
  }
}
```

qid 对应词库行号（去重后的代表行号）。

#### answers：概率返回

```json
{
  "answers": {
    "q0001": { "type": "noul", "noul": 0.04 },
    "q0381": { "type": "noul", "noul": 0.91 }
  },
  "usage": { "input_tokens": 86000 }
}
```

- `noul`：该标签被提及的概率（0~1）；
- `usage.input_tokens`：本次请求的输入 token 数（用于成本核算）。

### 6.2 概率如何转换成两个 CSV

#### 17 列预测细分表

默认阈值 τ=0.5：

```text
noul ≥ 0.5 → 命中，写入细分表
noul < 0.5 → 不命中，不写
```

逐列映射：

| 列 | 来源 |
| --- | --- |
| 样本号、平台 | meta.json |
| 词库原始行号 | qid 数字部分 + 1 |
| 标签ID | 词库行号关联已知 ID；无 ID 留空 |
| 类别、细分类别、标签 | qid 反查 `label_lexicon.json` |
| 评价/提及对象 | 固定 `未提取`（Jev 不输出文本） |
| 表达类型 | 固定 `未提取` |
| 证据字段 | 命中关键词回搜定位到 title/content/OCR 等来源字段 |
| 原文证据 | 命中位置前后约 30 字；找不到则空 |
| 情绪 | 证据位置 ±near 窗口查正/负向词表（规则派生） |
| 情绪来源 | `窗口定位` 或 `未定位` |
| **Jev概率** | **直接取 answers[qid].noul** |
| 命中阈值 | 本次使用的 τ（默认 0.5） |
| 模型版本 | API 响应的 model 字段 |
| API来源 | 实际请求的 base_url |

#### 12 列预测汇总表

每个样本一行：

| 列 | 来源 |
| --- | --- |
| 样本号、平台 | meta |
| 帖子ID（文本） | v3 的 id（字符串） |
| CSV记录序号 | v3 的 csv_row_no |
| 发布时间 | v3 的 publish_time |
| 文本字符数 | v3 的 char_count_raw |
| 入样原因 | 抽样清单 → meta.json |
| 部分标签 | 命中标签名前 8 个；超过追加"另N项见明细" |
| 标签证据数 | 该样本写入细分表的行数 |
| 灰区待复核数 | 概率落在 [0.3, 0.7] 的数量 |
| 截断标记 | 超过 2,000 字为"是" |
| 原帖链接 | v3 的 url |

## 8. 后续优化选项（生产阶段再考虑）

当成本或延迟成为瓶颈时（例如日处理 200 万条），可以考虑以下先进方法：

### 8.1 语义检索 + Jev 验证（RAG 模式）

- 成本：约 ¥40/万条（节省 85%）；
- 适用：日处理 >100 万条；
- 风险：依赖嵌入模型质量，可能漏召回。

### 8.2 混合正则 + Jev

- 成本：约 ¥100/万条（节省 61%）；
- 适用：日处理 20-100 万条；
- 风险：需要维护两套逻辑。

### 8.3 两级 Jev（投机细化）

- 成本：约 ¥200/万条（节省 23%）；
- 适用：需要纯 Jev 方案但想省成本；
- 风险：节省幅度最小，实现复杂。

### 8.4 H 级联（类别门控）

- 成本：约 ¥49/万条（节省 81%）；
- 适用：类别分布稀疏的场景；
- 风险：门控可能漏召回，需要回退机制。

**当前阶段不需要实现这些方法。** 等 10,000 条 A2 基线出来后，再根据业务需求决定是否优化。

## 9. 已知限制

- Jev 不生成文本，所以判断说明、内容简述不纳入预测表；
- 语义命中可能没有字面证据，证据/情绪会标为未定位；
- 单请求问题多、token 成本高（生产阶段可优化）；
- 官方与部分中转端点模型版本可能不同，预测表保留版本和 API 来源；
- 打标结果是否准确，不在本文下结论，由独立测试方案评估。

### 9.1 2026-11-16 实测补充

| 方案 | 问题数/帖 | 实测准确率 | 实测召回率 | 备注 |

**A2 阈值曲线（同一批 raw 重算，0 成本）：**

| tau | P | R | F1 | 预测数 |
| --- | --- | --- | --- | --- |
| 0.5 | 35.5% | 80.6% | 0.493 | 4,095 |
| **0.6（当前）** | 39.4% | 77.0% | 0.521 | 3,528 |
| 0.7 | 44.0% | 73.8% | 0.551 | 3,029 |

**三条由此得出的结论：**

1. **粗筛不是"无损省钱"。** B 在 tau=0.6 是 P 49.5 / R 37.5，A2 在 tau=0.8 是 P 50.2 / R 68.7
   —— 同样的准确率，召回高一倍。B 的粗筛把召回砍掉了约 31 个百分点，代价是 26 倍 token 差异。
2. **Jev 自身召回上限 = 77%（tau=0.6）/ 85%（tau=0.3）。** A2 的 415 个漏标 **全部送问过**
   （FN 未送问 = 0），是模型给了 <0.6 的概率，不是流程问题。
3. **95% 目标不是调参能到的。** 最优工作点 P 50.2 / R 68.7，两轴都离 95% 很远；瓶颈在
   「Jev noul 判定与 LLM 初稿口径的一致性」，不在筛选层。要么换金标准人审，要么接受
   「Jev 只做候选召回、人工/二次模型定稿」的分工。

**成本口径（实测，官方 API $0.042/M input）：**

| 方案 | 100 条 tok | 100 条成本 | 单帖 | 20 万帖/天 | 200 万帖/天 |
| --- | --- | --- | --- | --- | --- |
| B | 243,480 | ¥0.07 | ¥0.0007 | ¥147/天 | ¥1,473/天 |
| A2 | 6,382,818 | ¥1.93 | ¥0.019 | ¥3,860/天 | ¥38,603/天 |

评测口径说明：

- P/R/F1 按 **(样本号, 标签)** 唯一对计算。金标准 2,475 行 → 唯一 **1,805** 对。
- 去重判据是 **「样本号 + 标签 + 评价/提及对象」**，**原文证据不参与判断**（证据由 LLM
  生成，同一标签同一对象在不同句子各标一次仍算重复，证据合并到一行）；同一标签挂在
  不同对象上（一帖多产品/多品牌）各自保留，品牌提及 541 行即属此类。
- 金标准已用 `tools/normalize_gold.py` 归一：词库把同一概念拆成多个行号（8 组，
  如 `功效/抗老/改善暗沉` = 130、138），已统一到组代表行号，原值留在
  `原始词库行号（未归一）` 列。未归一前是 1,963 对，其中 158 个落在"非代表行号"上、
  模型永远答不到，会把召回率低估约 3 个百分点。
- 旧版 `jev_eval.py` 把"金标准行级 TP"与"预测标签级 FP"混算，准确率被虚高成 63.2%，已修正。
- 详见 `core/README.md` 与 `out/评测报告_B_A2.md`。

### 9.3 指标口径敏感性（2026-11-16 补，同一批 raw_A2 重算，0 成本）

测试方案 §2 把"95% 指标"列为待确认项（标签级 micro-F1 / 标签命中率 / 帖子级全对率，三者不可混用）。
用现有 100 条 raw 按三种口径分别算，**结论差 50 倍以上**，这条必须先定，否则任何"达标/不达标"都不成立：

| 口径 | tau=0.6 | tau=0.8（F1 最优） | 离 95% 的距离 |
| --- | --- | --- | --- |
| ① 标签级 micro（(样本,标签) 对级，现报告口径） | P 39.4% / R 77.0% / F1 0.521 | P 50.2% / R 68.7% / F1 0.580 | 两轴都差 17~55 个点 |
| ② 帖子级全对率（预测集合与金标准完全一致） | **1.0%（1/100）** | **2.0%（2/100）** | 差约 50 倍，无讨论余地 |
| ③ 帖子级宏平均（逐帖算 P/R 再平均） | P 42.6% / R 79.8% | P 55.8% / R 71.5% | 与 ① 不同但同量级 |

②的含意：100 帖里只有 1~2 帖的标签集合与 LLM 初稿完全一致。若业务要的是"整帖标签全对"，则 Jev 这条路在当前标签体系下不可行，与提示词无关 —— 638 个标签里平均每帖命中 18 个，**要求 18 个全对，任何单模型都做不到**。建议验收口径锁定 ①（标签级 micro），并在报告里注明"不是帖子级全对"。

**灰区人审成本被低估（同一批 raw 测算）**：

- 建议改为"灰区只做抽检校准"（每批抽 200~500 对估偏差），不承诺全量人审；`12 列汇总表` 的"灰区待复核数"列应降级为**观测指标**，不作为人审工作量承诺。
