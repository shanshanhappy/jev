## 1. 核心任务

对 `data\抽样清单.csv` 指定的帖子，调用 Jev API 判断每个标签是否被提及，生成 17 列预测细分表和 12 列预测汇总表。

**所有标签命中结论均来自 Jev API 返回的概率。** 本地代码负责准备请求、发送 API、保存响应、按阈值转换概率、辅助生成证据和情绪。

## 3. Jev 问题类型选择：Noul vs Choice vs Score

| 原语 | 模型回答 | 适合任务 | 是否适合本次 638 标签主任务 |
| --- | --- | --- | --- |
| **Noul（判断）** | 是/否概率（0~1） | 是非判断、条件清单、多标签命中 | **适合** |
| **Choice（选择）** | 从选项中选一个 + 各选项概率 | 单选分类、路由 | **不适合**：一条帖子可命中多标签，不能只选一个 |
| **Score（打分）** | 在有序等级中选一个 | 严重程度、满意度 | **不适合**：词库没有为每个标签定义统一强度等级 |

**选 Noul 的四个理由**：
1. 多标签任务，一条帖子可命中多个标签；
2. 需要独立概率做阈值和灰区；
3. 不需为每个标签构造"命中/未命中"两选项；
4. 词库没有评分标尺。

Choice/Score 留作辅助字段：后续补产"表达类型""情绪"等互斥属性时用 Choice；增加"严重程度"等有序指标时用 Score。

### 4.1 方案 A1：全量纯语义（638 问）

**思路**：每个标签只问"是否提到「X」（类别）？"不加任何词库命中/排除提示。

**用途**：测量 Jev 的裸语义能力上限——不借助词库提示时能得多少分。

**token/帖**：约 27k（state 约 4k + 638 × 35 tok/问）。

**10,000 条成本**：约 ¥138。

### 4.2 方案 A2：全量+词库提示（638 问）⭐ 当前推荐

**思路**：每个标签问"是否提到「X」（类别）？常见说法如 A、B、C，同义改写也算；若语境是否定/排除含义则不算。"

**用途**：Jev 效果基准——给出"Jev 在词库辅助下能做到多少分"的上限。

**token/帖**：约 86k（state 约 4k + 638 × 130 tok/问）。

**10,000 条成本**：约 ¥259。

### 4.3 方案 B：词库粗筛后 Jev（约 30 问）

**思路**：先用词库规则（命中关键词 + 且词 + 排除词）在本地做正则匹配，只对命中的标签调用 Jev 验证。

**token/帖**：约 5k（只有命中的候选标签进入 API）。

**10,000 条成本**：约 ¥16。

**优点**：成本极低，适合预算紧张或大批量。
**缺点**：
- 纯语义标签（108 行命中词与标签名零交集）天然漏掉；
- 谐音黑话（m感/k氧/早C晚A）正则匹配不到；
- 召回上限受限于正则覆盖率。

**📊 2026-11-16 实测修正（100 条，tau=0.6，对齐 LLM 初稿金标准）**

| 指标 | 实测值 |
| --- | --- |
| 准确率 P | **49.5%**（677 / 1,368） |
| 召回率 R | **37.5%**（677 / 1,805） |
| F1 | 0.427 |
| 字面匹配召回天花板 | **71.2%** |

三个必须先认清的事实：

1. **B 方案在结构上不可能达到 95%。** 金标准 1,805 个标签里只有 1,285 个能在原文找到
   词库关键词的字面形式，剩下 520 个是同义改写/隐含表达，字面粗筛永远捞不到。
2. **召回问题 95% 出在粗筛，不在模型。** 1,128 个漏标里有 1,076 个是"压根没送进模型"，
   只有 52 个是送问了却没判对。
3. **准确率 49.5% 才是 Jev 自身的问题。** 送问的 1,368 个标签里有 691 个假阳性，
   要靠问题措辞优化或收窄金标准口径来解决。

**已修复的两个实现缺陷**（详见 `core/README.md` §3）：

- 排除词旧版按全文匹配：362 个标签共用"不/没/没有/没用…"这套通用否定词，
  中文帖子几乎都含"不"字，候选被大面积误杀（每帖候选 21.1 → 修复后 34.4）。
- 粗筛用 `full_text` 全文、送模型只送前 2000 字：在 2000 字之外命中的标签会被提问，
  但模型从来看不到那段文字，必然判 0。

**定位建议**：B 方案可保留为"低成本预筛层"，但不能作为独立交付方案去承诺 95% 准确率。

### 4.4 方案 H：两级级联（类别门控 → 候选标签）

**思路**：
1. 第 1 次请求：问 41 个类别（Noul）；
2. 保留概率 ≥0.15 的类别 + Top-12 类别；
3. 第 2 次请求：只对候选类别下的叶子标签提问。

**token/帖**：约 16k（请求 1: ~2k + 请求 2: ~14k）。

**10,000 条成本**：约 ¥49（理想情况节省 81%）。

**优点**：纯 Jev 方案，不依赖正则/嵌入；大幅降本。
**缺点**：
- 门控可能漏召回（类别答错→整组子树消失）；
- 需要回退机制（门控不确定时回退全量）；
- 多次请求重复发送 state，抵消部分节省；
- 实现复杂（需要多轮请求编排）。

**实测数据**（理想父级全对时）：
- 两级（类别→标签）：平均 253 问/帖；
- 三级（类别→细分类别→标签）：平均 181 问/帖。

### 4.5 方案 RAG：语义检索 + Jev 验证（Top-50 标签）

**思路**：
1. 预计算 638 个标签描述的向量嵌入（一次性成本）；
2. 对每条帖子计算向量嵌入；
3. 余弦相似度取 Top-50；
4. 只对 Top-50 调用 Jev 验证。

**token/帖**：约 8k（50 问 × 130 tok + state 约 1.5k）。

**10,000 条成本**：约 ¥40（节省 85%）。

**优点**：最现代、最通用、不需要手写规则；大幅降本。
**缺点**：
- 需要额外嵌入模型 API（如 OpenAI text-embedding-3-small）；
- 可能漏掉"字面相似但语义不同"的标签；
- 依赖嵌入质量，召回不可控。

> ⚠️ **实现状态（2026-11-16 核查）**：`core/schemes.py` 的 `SchemeRAG` **尚未按上述流程实现**。
> 其中的 `similarity()` 是「词库关键词命中覆盖率」（命中词数 / 该标签词数），不是向量余弦相似度，
> 全项目 0 处 embedding 代码。后果是排序偏向"关键词表短"的标签：220 个只配 1 个关键词的标签，
> 命中即 1.00 分排最前；S001 里命中 8 个关键词的「眼周」只有 0.38 分。
> 100 条实测 Top-50 平均 36.4 个候选，与 B 的 34.4 几乎等价（差异 +10.0 / −8.0 抵消），
> token 4,489 vs 4,342。**跑出来的数字不能当作"语义检索"结论。**
> 同类问题：`H` 的 leaf 阶段没有按 gate 结果过滤（注释已承认）、`Speculative` 的 pass2 也是全量、
> `Hybrid` 的"语义标签"是固定的 75 个（与帖子无关）。这 4 个方案在补实现前不宜进入选型对比。

### 4.6 方案"混合"：正则 + Jev（约 200 问）

**思路**：
1. 用词库正则匹配所有能匹配的标签（约 400 个，零成本）；
2. 精确匹配且上下文符合 → 直接接受；
3. 精确匹配但有否定词/歧义 → 送 Jev 验证（约 100 个）；
4. 无匹配但在"纯语义标签"集合中 → 送 Jev 判断（108 个）；
5. Jev 总问题数约 200。

**token/帖**：约 16k。

**10,000 条成本**：约 ¥100（节省 61%）。

**优点**：最实用、不需要额外 API、召回可控。
**缺点**：需要维护两套逻辑（正则+Jev），工程复杂度高。

### 4.7 方案"投机"：两级 Jev（638 → 150 问）

**思路**：
1. 第一遍用 A1 简短指令（638 问，约 27k token）；
2. 只对概率在 [0.2, 0.8] 的"边界标签"用 A2 详细指令（约 150 问）；
3. 边界标签用 A2 概率，其余用 A1 概率。

**token/帖**：约 32k（A1: 27k + A2 边界: ~5k）。

**10,000 条成本**：约 ¥200（节省 23%）。

**优点**：纯 Jev 方案，不需要其他模型。
**缺点**：节省幅度最小，实现复杂（需要两轮请求编排）。

## 6. A2 方案的详细设计

### 6.1 调用 Jev 时的核心结构

#### state：帖子内容

```json
{
  "平台": "小红书",
  "内容": "【标题】……\n【正文】……\n【图片文字】……"
}
```

- 平台：从 v3 的 `site_name` 读取；
- 内容：从 v3 的 `full_text` 读取，最多 2,000 字；超长截断并在 meta 中标记。

**不发送**：金标准、入样原因、词库行号（这些只用于本地后处理）。

#### questions：638 个标签问题

每个标签一个 Noul，格式示例：

```json
{
  "q0001": {
    "type": "noul",
    "instructions": "这篇社媒内容是否提到了「干皮」（肤质类型）？常见说法如干皮、干燥、爆皮、起皮、脱皮、掉皮，同义改写也算。若语境是不干皮、不是干皮等否定/排除含义则不算。"
  }
}
```

qid 对应词库行号（去重后的代表行号）。

#### answers：概率返回

```json
{
  "answers": {
    "q0001": { "type": "noul", "noul": 0.04 },
    "q0381": { "type": "noul", "noul": 0.91 }
  },
  "usage": { "input_tokens": 86000 }
}
```

- `noul`：该标签被提及的概率（0~1）；
- `usage.input_tokens`：本次请求的输入 token 数（用于成本核算）。

### 6.2 概率如何转换成两个 CSV

#### 17 列预测细分表

默认阈值 τ=0.5：

```text
noul ≥ 0.5 → 命中，写入细分表
noul < 0.5 → 不命中，不写
```

逐列映射：

| 列 | 来源 |
| --- | --- |
| 样本号、平台 | meta.json |
| 词库原始行号 | qid 数字部分 + 1 |
| 标签ID | 词库行号关联已知 ID；无 ID 留空 |
| 类别、细分类别、标签 | qid 反查 `label_lexicon.json` |
| 评价/提及对象 | 固定 `未提取`（Jev 不输出文本） |
| 表达类型 | 固定 `未提取` |
| 证据字段 | 命中关键词回搜定位到 title/content/OCR 等来源字段 |
| 原文证据 | 命中位置前后约 30 字；找不到则空 |
| 情绪 | 证据位置 ±near 窗口查正/负向词表（规则派生） |
| 情绪来源 | `窗口定位` 或 `未定位` |
| **Jev概率** | **直接取 answers[qid].noul** |
| 命中阈值 | 本次使用的 τ（默认 0.5） |
| 模型版本 | API 响应的 model 字段 |
| API来源 | 实际请求的 base_url |

#### 12 列预测汇总表

每个样本一行：

| 列 | 来源 |
| --- | --- |
| 样本号、平台 | meta |
| 帖子ID（文本） | v3 的 id（字符串） |
| CSV记录序号 | v3 的 csv_row_no |
| 发布时间 | v3 的 publish_time |
| 文本字符数 | v3 的 char_count_raw |
| 入样原因 | 抽样清单 → meta.json |
| 部分标签 | 命中标签名前 8 个；超过追加"另N项见明细" |
| 标签证据数 | 该样本写入细分表的行数 |
| 灰区待复核数 | 概率落在 [0.3, 0.7] 的数量 |
| 截断标记 | 超过 2,000 字为"是" |
| 原帖链接 | v3 的 url |

### 7.1 成本预估

- 10,000 条 × 86k token/帖 = 860M token；
- 官方价格 $0.042/M token = **$36.1 ≈ ¥259**；
- 预计耗时：2-3 小时（受 API 限流影响）。

### 7.2 结果核对

1. `out\raw\` 中每个成功样本是否有 `body.answers`；
2. answers 的 qid 是否能对应回词库标签；
3. 细分表行数是否等于汇总表"标签证据数"；
4. 细分表的 `Jev概率` 是否与 raw 中对应 qid 的 `noul` 一致；
5. 未命中标签是否没有混入细分表；
6. 入样原因、截断标记、模型版本、API来源是否齐全。

## 8. 后续优化选项（生产阶段再考虑）

当成本或延迟成为瓶颈时（例如日处理 200 万条），可以考虑以下先进方法：

### 8.1 语义检索 + Jev 验证（RAG 模式）

- 成本：约 ¥40/万条（节省 85%）；
- 适用：日处理 >100 万条；
- 风险：依赖嵌入模型质量，可能漏召回。

### 8.2 混合正则 + Jev

- 成本：约 ¥100/万条（节省 61%）；
- 适用：日处理 20-100 万条；
- 风险：需要维护两套逻辑。

### 8.3 两级 Jev（投机细化）

- 成本：约 ¥200/万条（节省 23%）；
- 适用：需要纯 Jev 方案但想省成本；
- 风险：节省幅度最小，实现复杂。

### 8.4 H 级联（类别门控）

- 成本：约 ¥49/万条（节省 81%）；
- 适用：类别分布稀疏的场景；
- 风险：门控可能漏召回，需要回退机制。

**当前阶段不需要实现这些方法。** 等 10,000 条 A2 基线出来后，再根据业务需求决定是否优化。

## 9. 已知限制

- Jev 不生成文本，所以判断说明、内容简述不纳入预测表；
- 语义命中可能没有字面证据，证据/情绪会标为未定位；
- 单请求问题多、token 成本高（生产阶段可优化）；
- 官方与部分中转端点模型版本可能不同，预测表保留版本和 API 来源；
- 打标结果是否准确，不在本文下结论，由独立测试方案评估。

| tau | P | R | F1 | 预测数 |
| --- | --- | --- | --- | --- |
| 0.5 | 35.5% | 80.6% | 0.493 | 4,095 |

**三条由此得出的结论：**

1. **粗筛不是"无损省钱"。** B 在 tau=0.6 是 P 49.5 / R 37.5，A2 在 tau=0.8 是 P 50.2 / R 68.7
   —— 同样的准确率，召回高一倍。B 的粗筛把召回砍掉了约 31 个百分点，代价是 26 倍 token 差异。
2. **Jev 自身召回上限 = 77%（tau=0.6）/ 85%（tau=0.3）。** A2 的 415 个漏标 **全部送问过**
   （FN 未送问 = 0），是模型给了 <0.6 的概率，不是流程问题。
3. **95% 目标不是调参能到的。** 最优工作点 P 50.2 / R 68.7，两轴都离 95% 很远；瓶颈在
   「Jev noul 判定与 LLM 初稿口径的一致性」，不在筛选层。要么换金标准人审，要么接受
   「Jev 只做候选召回、人工/二次模型定稿」的分工。

评测口径说明：

- P/R/F1 按 **(样本号, 标签)** 唯一对计算。金标准 2,475 行 → 唯一 **1,805** 对。
- 去重判据是 **「样本号 + 标签 + 评价/提及对象」**，**原文证据不参与判断**（证据由 LLM
  生成，同一标签同一对象在不同句子各标一次仍算重复，证据合并到一行）；同一标签挂在
  不同对象上（一帖多产品/多品牌）各自保留，品牌提及 541 行即属此类。
- 金标准已用 `tools/normalize_gold.py` 归一：词库把同一概念拆成多个行号（8 组，
  如 `功效/抗老/改善暗沉` = 130、138），已统一到组代表行号，原值留在
  `原始词库行号（未归一）` 列。未归一前是 1,963 对，其中 158 个落在"非代表行号"上、
  模型永远答不到，会把召回率低估约 3 个百分点。
- 旧版 `jev_eval.py` 把"金标准行级 TP"与"预测标签级 FP"混算，准确率被虚高成 63.2%，已修正。
- 详见 `core/README.md` 与 `out/评测报告_B_A2.md`。
